# ZUL @{...} binding sweep log

Started 2026-08-18. Scope: all `.zul` files under `libreplan-webapp/src/main/webapp` using the
old-style `@{...}` ZK binding shorthand, which never registers with this app's AnnotateBinder
(needs `@load(...)`/`@save(...)` instead). Companion to the fixes already made this session to
unittypes, qualityforms, workreports (Cost menu first 3 + workReport.zul), costcategories,
typeofworkhours (list only), expensesheet.

Candidate count at sweep start: 98 files with at least one real (non-layout) `@{...}` binding and
no `@load`/`@save` anywhere in the file. `reports/` (8 files) confirmed in-scope: real
`apply="...Controller"` ZK pages, same AnnotateBinder pipeline, not a separate JasperReports-only
mechanism.

Format per file: **path** — symptom found — fix applied — build result — live test result (PASS/FAIL
+ screenshot refs). Files that turn out to be false positives (e.g. dead/unreferenced, or the
`@{...}` usage is actually safe) are logged as SKIP with reason.

### Separate finding: Hibernate second-level cache returning corrupted entities

Discovered via the labels/_editLabelType.zul fix above: `LabelTypeModel.getLabels()` (never
previously executed - dead binding) fetches the same `Label` rows twice per request. First fetch:
fully populated. Second fetch, same rows: **every field null**, not just associations - confirmed
via direct DEBUG logging of the fetched entities before/after. `Label`/`LabelType` are mapped with
`<cache usage="nonstrict-read-write"/>` (Labels.hbm.xml). `libreplan-business-hibernate.cfg.xml`
already documented that an earlier session of this migration had to swap the L2 cache provider
from `EhCacheRegionFactory` (never reached GA for Hibernate 6) to `JCacheRegionFactory`, falling
back to JCache's default CacheManager since the old ehcache.xml is 2.x-schema and unreadable by
the new provider. That combination appears to hand back hollow entities on a second same-request
read instead of throwing or reloading from DB - a real data-correctness bug, not just a UI issue,
and potentially affecting any of the 8 `<cache usage="...">`-mapped entities in libreplan-business
under the right access pattern, not just Label/LabelType.

**Fix applied (user-approved, simplest/safest option)**: disabled second-level cache entirely -
`hibernate.cache.use_second_level_cache` set to `false` in `libreplan-business-hibernate.cfg.xml`.
Rebuilt+reinstalled libreplan-business, rebuilt webapp against it. Confirmed fix: label edit form
now shows all 8 labels correctly on every load (was: NPE crash before this fix, even after the
binding fix, due to this separate bug). Proper root-cause/reconfiguration of L2 caching (if wanted
back for performance) is explicitly deferred, per user's choice.

### New bug class found this batch: `Util.createBindingsFor`'s hardcoded `"controller"` attribute name

Every controller fixed in Batches 1-5 happened to use `comp.setAttribute("controller", this)` as
its own convention already. `PasswordController`/`SettingsController` predate that convention and
used a page-specific name (`passwordController`/`settingsController`) instead - which is what the
ZUML's binding expressions actually reference, and works fine for plain EL variable resolution
(`onClick="passwordController.save()"` etc still resolves correctly via ZK's normal
attribute/fellow lookup) - but `Util.createBindingsFor` specifically needs a component attribute
named exactly `"controller"` to find the object to bind against, regardless of what the ZUML
expressions themselves are called. Worth grepping for `comp.setAttribute("controller"` across any
remaining files before assuming a `createBindingsFor`/`reloadBindings` addition is sufficient -
if the controller doesn't already set that literal attribute name, the reload will silently no-op
exactly like `EntryPointsHandler`'s bug above, with no crash and no obvious symptom other than
"nothing appears bound."

## Out-of-band bug report (2026-08-18, user-reported): "Hours type" column in Timesheet lines grid (workReport.zul)

User reported, while editing a timesheet: the "Hours type" column showed no value for existing
lines (should default to "Default"), and picking a value in one row made every other row's
dropdown jump to the same value. Not part of the `@{...}` binder sweep - this grid's rows are
built entirely imperatively in `WorkReportCRUDController.WorkReportListRenderer` (Java
`RowRenderer`, no ZUML bindings at all) - a different bug class from the rest of this log, found
and fixed in the same session as a direct request, not part of the systematic sweep.

**Root cause 1 (the cross-row contamination the user reported)**: `appendHoursType(Row)` built
ONE shared `SimpleListModel` field (`allHoursType`, populated once in `initializeHoursType()`)
and called `lbHoursType.setModel(allHoursType)` for *every* row's Listbox - the same instance,
every time. `org.zkoss.zul.SimpleListModel` extends `AbstractListModel`, which implements
`org.zkoss.zul.ext.Selectable<E>` and stores the current selection **inside the model instance
itself** (`protected transient Set<E> _selection`), not in the widget. Confirmed via `javap` on
the ZK 10.3.0.1-jakarta jar. Selecting an item in any row's Listbox mutated that one shared
model's selection state, which every other row's Listbox (bound to the identical instance) then
reflected too. Fixed by giving every row's Listbox its own fresh model built from the same
underlying `List<TypeOfWorkHours>` (changed the `allHoursType` field itself from
`ListModel`/`SimpleListModel` to a plain `List<TypeOfWorkHours>`, wrapped per-row).

**Root cause 2 (the "no values shown" the user also reported)**: independently, the pre-existing
selection logic - `Listitem.setSelected(true)` / `Listbox.selectItem(item)` called imperatively
*after* `renderAll()`, on a Listbox not yet attached to the row/page - never produced a visible
`<option selected>` in the client HTML, even though the Java-side flag was set correctly
(confirmed the DB value was non-null, "Default", the whole time via a temporary debug print -
this was never a data problem). Two different fix attempts (reordering `row.appendChild()`
earlier; setting selection on the model via `Selectable.addToSelection()` before `renderAll()`)
both failed to fix the visible selection (the first crashed with an unrelated NPE from a
mid-render item-value reset, the second silently still rendered blank). What actually worked:
replaced the whole "renderAll() then imperatively select" approach with a `ListitemRenderer` that
sets `item.setSelected(...)` **while each Listitem is being constructed** (comparing
`TypeOfWorkHours.toString()`, i.e. by name, not `.equals()` - `TypeOfWorkHours` has no
equals()/hashCode() override, and the value from `workReportLine.getTypeOfWorkHours()` is almost
never the same object instance as its counterpart in the options list). This is the same
`ListitemRenderer`-driven-selection pattern already working elsewhere in this codebase (e.g.
`IssueLogCRUDController`'s enum renderers).

**Downstream effect also fixed for free**: since `setHoursType()` (which persists the selection
onto the `WorkReportLine` entity) was never actually reached before - the ON_SELECT listener only
existed on a Listbox whose visible state didn't match its Java state anyway, and the debug prints
confirmed the entity's `typeOfWorkHours` field genuinely never got updated - "Add new row" (which
re-renders the whole grid from the underlying entities) appeared to "reset" any Hours-type choice
made moments earlier. That was never a separate discard-on-refresh bug: it was the same root
cause. Verified live: select Overtime on one row, click "Add new row" (grid fully re-renders) -
the Overtime selection now genuinely survives, because it was actually persisted to the entity
this time.

### New bug class found this batch: shared macro components (calendars/_edition.zul) reused across multiple controller classes

`calendars/_edition.zul` is reused in (at least) three places: the standalone Calendars admin page
(`BaseCalendarCRUDController`, already fixed in an earlier session), and embedded inline inside
both `WorkerCRUDController`'s and `MachineCRUDController`'s own "Calendar" tab (via
`BaseCalendarEditionController`, a separate, simpler composer applied specifically to the embedded
`editCalendarWindow` subtree). Live-testing the Worker Calendar tab crashed with
`PropertyNotFoundException: baseCalendarCodeAutogenerated not found on WorkerCRUDController`.

Root cause, confirmed through direct experimentation (not just static reading): **AnnotateBinder
captures its "controller" object once, at binding-*registration* time (`Util.createBindingsFor`),
not freshly at each `Util.reloadBindings` call.** The page-wide `Util.createBindingsFor(comp)`
call in `WorkerCRUDController.doAfterCompose` walks the *entire* subtree at initial page load,
including the (at that point invisible) embedded `editCalendarWindow`, and captures
`WorkerCRUDController` as the controller for every binding found there too - permanently, since
`Util.createBindingsFor`'s own re-entry guard (`if (result.getAttribute("binder") != null)
return`) blocks any later, more narrowly-scoped registration attempt for a component that
inherited a binder from an ancestor's earlier walk. Setting a local `"controller"` attribute
later (shadowing the outer one for normal EL/fellow lookups) does **not** change which controller
an *already-registered* binding evaluates against.

Two more targeted fixes were tried and both had worse side effects than the problem:
1. **Local attribute alone** (no new binder) - silently ineffective, same crash.
2. **`comp.setAttribute` + a nested `Util.createBindingsFor(editCalendarWindow)`** - *did* fix the
   Calendar tab, but broke a *different*, unrelated binding elsewhere on the same page
   (`userBindingGroupbox`'s `notLimitingOrVirtualResource`, on the Personal Data tab, started
   resolving against the calendar sub-controller instead of `WorkerCRUDController`) once the
   outer `Util.reloadBindings(editWindow)` (called later by `showEditWindow()`) ran and
   recursively touched the nested subtree again. Not chased further to a root cause given the
   depth of ZK internals involved - reverted.

**What actually worked**: leave `BaseCalendarEditionController` itself untouched (still no local
"controller" attribute, no nested binder) and instead add the missing property directly to
`WorkerCRUDController` (`isBaseCalendarCodeAutogenerated()`/`setBaseCalendarCodeAutogenerated(
boolean)`, thin delegating wrappers to `baseCalendarEditionController`'s own already-existing
same-named methods) - since the *entire* page, calendar tab included, was always resolving
"controller" to `WorkerCRUDController` anyway (that's the actual, if unintuitive, working
behavior), the fix is simply to make sure `WorkerCRUDController` itself exposes every property the
embedded macro needs, rather than fighting to redirect resolution elsewhere. `MachineCRUDController`
has the exact same embedding and is very likely missing the same property - not yet confirmed
live, flagged for when the machine batch is reached.

PASS after this fix - screenshot fix-worker-edit3.png (full Personal Data tab, including the
previously-never-working bound-user selection showing "Tobias (Tobias H)" / "test@1.local"
correctly) and fix-worker-calendar-tab.png (Calendar tab: calendar picker, exception form,
exceptions list, all rendering with no error).

**Lesson for the rest of this sweep**: any `.zul` file reused via `<?component name="x"
macroURI="..."?>` + inline embedding inside MULTIPLE different pages/controllers is a higher-risk
case than a page with a single, dedicated controller - the "controller" property resolution can
silently depend on registration order in ways that aren't visible from reading the ZUML alone.
Worth specifically re-testing any such shared macro from *each* of its embedding contexts, not
just the first one that happens to get fixed.
